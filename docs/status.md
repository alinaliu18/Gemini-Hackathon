## 2 这一轮做了什么

**前端构建并跑通。** c0caf91 的前端能构建。在无头浏览器里接真后端代码跑了两条完整流程，只把 Gemini 换成固定回答。

练习这条是首页进 Quick Practice，没填齐时开始按钮是灰的，岗位描述太短会说差几个词，练完一次拿到报告，第二次弹出注册框，注册完能接着练，刷新以后还是登录状态。

面试这条用 Chromium 的假麦克风和假摄像头，再伪造一个 Gemini Live 服务端，按真模型的方式提问、送回候选人的话、调用追问工具。跑下来面试官 3 次调用工具，拿到的结果依次是追问、追问、换题，每题最多 2 次的上限生效了。之后报告流式出来，报告底下提议下一场，点同意下载到日历邀请，用邀请里的链接打开，Setup 顶上显示这一场先练哪一项。

跑的时候修了 3 个问题。第二次练习要求登录时，弹框底下还多一条一样内容的红色报错，去掉了。同意下一场的接口，在两个人都没登录时能拿别人的报告生成计划，是一个空值比较写错了，改了。默认邀请时间在半夜打开会变成凌晨 12 点，改成第二天傍晚 6 点。

**面试官的追问。** 不再每题固定追问一次。每个回答后判断缺什么，具体例子、本人行动、结果数字，缺什么问什么，不缺就换题，每题最多 2 次。做法和原计划不一样，原因在 `docs/tech-notes.md` 第 6 节。简单说就是从旁边推送决定来不及，面试官判断回答结束到开口只有 0.4 到 0.8 秒，所以直接改成挂工具，面试官调用工具，等结果再开口。决定还是后台文本模型做的。超时 2 秒就退回每题追问一次，每次决定都记表，不记回答原文。

**报告后提议下一场。** 报告底下提议下一场练分数最低的一项。用户点同意才生成日历邀请，不点什么都不存。邀请里的链接打开以后，Live 面试官和 Quick Practice 的第一题都会针对那一项。

**45 条评测集。** `eval/followup_cases.jsonl`。关键词基线跑出来准确率 89%，多余追问 0%，漏掉追问 18%。这个数偏高，回答和规则都是我写的，要用真实回答补，标注要你或者别人再看一遍。跑评测还发现原来的追问顺序不对，已经改成先问具体例子。

**测试。** 新增 `tests/test_agent.py` 和 `src/live/followup.test.mjs`。全部 9 个 Python 离线测试和 6 个 Node 测试通过。

**追问决定的耗时。** 这个数决定候选人每次回答后要多等多久。`python eval/run_followup_eval.py --model` 会打印中位数，同时出 45 条的准确率。45 次调用，要分 3 天，或者用付费 key。

**真模型会不会乖乖调用工具。** 伪造的 Live 服务端会调用工具，真的 gemini-3.8-live 会不会每次都调用、临时 token 里能不能带工具配置，只有真跑一场才知道。这一条是上线前最大的风险，建议拿到 key 先跑 `tests/live_smoke.py` 一次。

## 4 Cloud Run 出网，部署时要在控制台做的

代码这边，c0caf91 已经挡住了 `.run.app`、`.internal` 这类地址和元数据地址。部署时还要做 3 件事。

第 1 件，不给这个服务挂 VPC 连接器。这样它出网只能走公网，碰不到项目里的内网地址。

第 2 件，给它单独建一个服务账号，只给读那一个密钥的权限。万一有人绕过检查拿到元数据服务的令牌，能做的事也只有这一件。

第 3 件，同一个项目里别的 Cloud Run 服务，入口设成只允许内部访问。这个服务走公网访问不到它们。
